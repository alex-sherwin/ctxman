# Inflate v2 brief (user request, 2026-10-17): inflate into a WORKING DIRECTORY

The current Inflate produces one markdown blob. That is not sufficient. The inflate process must create a whole working
directory that an AI coding harness is pointed at as its root, with instructions markdown in the root and
cloned / vendored / symlinked content placed inside it. The generated instructions reference everything by concise,
precise RELATIVE paths with descriptions.

## User requirements (verbatim intent)
- **Inflate to <dir>**: the user picks a directory (may or may not exist). A backend handler ensures it exists and performs whatever the recipe calls for.
- **Remote repos** (reference remote-repo): default "mention repo in markdown"; option "clone repo" → clone into `<dir>/repos/<name>` AND mention it in the markdown at the location it was cloned to. A "primary" checkbox marks ONE cloned repo as the primary repo for this inflate (single-select: checking one unchecks the others). Recipe setting overridable in the Inflate tool at inflate time.
- **Local repo / folder** (reference local-repo): option "mention in markdown" or "symlink" → symlink to `<dir>/repos/<name>` AND mention it.
- **Skills**: the inflate copies the skill folders to `.agents/skills/<skill>/` (codex / generic) or `.claude/skills/<skill>/` (claude-code). (Remote skills: clone/download+extract into the same place.)
- **Combined markdown instructions**: target file configurable, default `<dir>/LLM_CONTEXT.md`.
- **OKF bundles** (kb, rca, idea, task, bug, feature, project): symlink the bundle into `<dir>/<dataset>/<slug>` (kb → `<dir>/kb/<slug>` etc.).
- Extrapolate other pertinent things: the LLM_CONTEXT.md synthesizes the map of contextual directories/files (what the primary repo is, other repos, installed skills, each okf bundle with its description, per-link guidance notes) with relative links.
- Commits at logical points are allowed.

## Orchestrator guidance for the planner
- Keep the existing markdown "render modes" as the way an item is REPRESENTED inside LLM_CONTEXT.md, and add a second axis, the MATERIAL mode, per item kind: what gets placed in the directory (none/mention, clone, symlink, copy, download+extract). Defaults when inflating to a dir: okf → symlink + pointer-with-relative-path; skill → copy into the harness skills dir + short mention; remote-repo → mention; local-repo → mention; remote-skill → install (clone or download+extract) into the skills dir. The old single-document render (no dir) must keep working (`/api/inflate/render`, Copy/Download) as a degenerate case with absolute paths.
- Recipe gains an `output` section (dir?, contextFile default `LLM_CONTEXT.md`, primary repo key?, material overrides) that the Inflate tool can override at run time without saving (run-time overrides layered on top of the recipe; show clearly what is overridden; offer "save overrides into recipe").
- Backend: `POST /api/inflate/run` performs the plan. Long operations (git clone, downloads) need progress: design a job model (start → job id; poll `GET /api/inflate/jobs/[id]` for step log/status; cancel) or SSE; justify. Cross-platform: spawn `git` with `shell:false`; symlinks on Windows use junctions for directories (`fs.symlink(target, path, 'junction')`); copying via `fs.cp` recursive; archives: decide the extraction approach for `.tar.gz`/`.tgz`/`.zip` (Node 24 has no built-in tar/zip; evaluate spawning `tar` (present on macOS/Linux/Windows 10+) vs adding a dependency; prefer `tar` CLI for tgz and a small dependency only if unavoidable for zip — verify availability on this Mac). Idempotent re-runs: existing clone → `git -C <path> pull --ff-only` (or fetch) or skip with a note; existing symlink → replaced if the target differs; skill copy → replaced; a `<dir>/.ctxman-inflate.json` manifest records what was placed so a re-run can remove items no longer in the recipe (only things the manifest says ctxman created — never delete anything else). Safety: dir must be absolute, not inside the ctxman repo's `data/`, `node_modules`, `.git`; refuse to run if the dir exists and is not empty and has no ctxman manifest UNLESS the user ticks "allow into non-empty dir".
- LLM_CONTEXT.md content: preamble (harness-aware), "Primary repository" section, "Repositories" (with relative paths, clone source, subpath hints), "Skills installed" (relative paths), one section per okf dataset with items (relative bundle path + main.md, description, state, guidance notes), ad hoc items, user markdown blocks in order; all links relative to the dir. Also consider (extrapolation, planner decides, keep small): a tiny `CLAUDE.md`/`AGENTS.md` stub in the dir that says "read LLM_CONTEXT.md first" when the harness looks for it, optional `.gitignore` for `repos/` when repos are cloned.
- UI (`/inflate`): an "Inflate to directory" panel: directory TextField with default (`~/ctxman-inflate/<recipe>` or last used, persisted per recipe in `output.dir`), context file name, per-item material controls appearing in the composition rows (Select for material mode; "Primary" checkbox visible only on cloned repos), Run button with a progress/step log panel (steps: mkdir, symlink x, clone y…, write LLM_CONTEXT.md), result summary with "Open in IDE" (reuse `POST /api/ide/open` from ROUND2_BACKEND_SPEC with an absolute dir instead of an entry) and "Copy path". Keep Preview for the markdown.
- Depends on round-2 kit changes (Select v2, GridList DnD) landing first for the UI; plan the UI against the ROUND2_UI_SPEC component names when that file exists, otherwise against the current kit and note it.
